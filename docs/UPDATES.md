# Обновления portable-версии

Источник: [flicherr/speeecial-snow-desktop](https://github.com/flicherr/speeecial-snow-desktop). Клиент обращается к `GET /repos/flicherr/speeecial-snow-desktop/releases/latest` без токена. Черновики, prerelease и версии не новее текущей не устанавливаются. Поддерживаются теги `vX.Y.Z` и `X.Y.Z`, сравнение числовое.

## Подготовка релиза

1. Согласуй версию в `src/version.hpp`, `CMakeLists.txt`, `resources/snowdesk.rc` и `resources/snowdesk.manifest`. В ресурсах четвёртый компонент — `0`. Строки меню и диагностики берутся из `version.hpp`.
2. Собери Windows x64 Release обычным `scripts/build.ps1`.
3. Выполни из корня репозитория:

   ```powershell
   .\scripts\package-release.ps1
   # Для Ninja или другого пути:
   .\scripts\package-release.ps1 -Executable '.\build\ninja-release\speeecial.exe'
   ```

4. Создай стабильный GitHub Release с соответствующим тегом, например `v1.0.10`, и приложи файлы из `dist\1.0.10`:

   | Файл | Назначение |
   |---|---|
   | `speeecial-windows-x64.exe` | **Обязателен для встроенного обновления.** Это отдельный asset, не файл внутри ZIP. Имя одинаковое в каждом релизе. |
   | `speeecial-1.0.10-windows-x64.zip` | Обычная portable-загрузка; внутри `speeecial.exe`. |
   | `SHA256SUMS.txt` | Необязательная ручная проверка скачанных файлов. |

Скрипт проверяет x64 и встроенную версию, но не публикует релиз. Установщик использует поле `assets[].digest` (`sha256:…`) из GitHub API, а не `SHA256SUMS.txt`. Если digest отсутствует, нет подходящего EXE или размер недопустим, клиент предлагает открыть релизы и скачать вручную. Старый ZIP-формат релизов менять не требуется.

Сохраняй обработку `--snow-updated` и подтверждение старта в последующих версиях: этот протокол нужен уже выпущенному помощнику. Удаление протокола приведёт к откату такой версии после ожидания подтверждения.

Первый переход с 1.0.9 и более старых версий выполняется вручную: в них ещё нет обновляющего кода. Проверить сетевой переход с 1.0.10 можно после появления более нового стабильного релиза с корректным EXE. Не публикуй фиктивную версию только ради теста; для процесса замены есть локальные тесты ниже.

## Поведение клиента

- Проверка при запуске включена по умолчанию; не чаще одного раза в 24 часа. Время последней попытки хранится даже после сетевой ошибки. Ручная команда обходит интервал. Изменение системных часов назад сбрасывает ограничение до новой попытки.
- Автоматической установки нет. После уведомления нужно нажать «Обновить до …». Проверка и загрузка выполняются в рабочем потоке. Процент загрузки виден при повторном открытии подменю.
- Настройка и отметка времени — `%LOCALAPPDATA%\SnowDesk\updates.ini`, отдельно от `settings.ini`. Ошибки записываются в ограниченный по размеру `snowdesk.log`. Ошибки автоматической сетевой проверки не открывают диалог и не сбрасывают графику.
- Сеть: системный WinHTTP, HTTPS с обычной проверкой сертификата, без cookies и передачи учётных данных Windows. Перенаправления разрешены только на перечисленные в коде GitHub/CDN-хосты. Нет отключения проверки TLS, встроенных токенов или внешней библиотеки HTTP.
- Ограничения: JSON до 2 МиБ, EXE до 128 МиБ, буфер передачи 64 КиБ, ограниченные тайм-ауты и число перенаправлений. При закрытии приложения рабочий поток получает отмену; UI не ждёт завершения DNS/HTTP. Поток владеет своим состоянием и не обращается к уничтоженному `App`.
- Проверяется точное имя asset, URL этого репозитория и тега, размер, SHA-256, PE x64 и встроенная версия EXE. SHA-256 подтверждает соответствие файлу из доверенного релиза; это не независимая цифровая подпись издателя.

## Замена и восстановление

1. Рядом с текущим EXE создаётся уникальная скрытая папка `.speeecial-update-{GUID}`. Файл скачивается как `payload.exe`; текущая программа копируется туда как `helper.exe`. Папка рядом обеспечивает тот же том для замены.
2. Вспомогательный процесс запускается с ограниченным списком наследуемых дескрипторов: старый процесс и два события. PID не используется как единственное доказательство завершения процесса. Помощник проверяет файл и подтверждает готовность.
3. Только после готовности UI даёт команду продолжить и штатно завершает приложение. Пока старый процесс жив, EXE не заменяется. Выход пользователя до подтверждения установки отменяет замену.
4. Помощник повторно проверяет SHA-256, сохраняет `previous.exe`, заменяет основной EXE через `ReplaceFileW` и запускает его с событием подтверждения старта. Имя и расположение пользовательского EXE сохраняются, в том числе после переименования.
5. Новая версия подтверждает готовность после создания трея и графики. Если процесс завершился или за 30 секунд не подтвердил старт, помощник завершает только запущенный им новый процесс, восстанавливает предыдущий EXE и пытается запустить его. Ошибка отображается сообщением.
6. После подтверждённого запуска папка помечается как завершённая. При следующем запуске завершённые папки этой portable-копии очищаются. После неудачного обновления резервная копия остаётся для ручного восстановления. Прерванная загрузка/аварийное выключение также могут оставить временную папку: после завершения приложения и помощника её можно удалить вручную; `previous.exe` сначала сохрани, если требуется восстановление.

Запись в защищённую папку и ошибки доступа не обходятся повышением привилегий. Перенеси приложение в доступную для записи папку или обнови вручную через пункт «Релизы на GitHub». Если восстановлению мешают антивирус, блокировка файла или отказ диска, резервный EXE остаётся в папке обновления. Защита от внезапного отключения питания на любом шаге не гарантируется; откат проверяет именно запуск, а не работу всех функций новой версии.

## Тесты

Переносимые тесты `snow_update_tests` входят в обычный CTest: порядок версий, prerelease/draft, неправильные/чужие asset URL, digest, размер, повреждённый JSON, дубли ключей/asset, лимит глубины и размера, интервал проверки, экранирование аргументов, согласованность версий.

На Windows можно собрать тесты реальных процессов и файловой замены без интернета:

```powershell
cmake --preset windows-msvc -DSNOWDESK_WINDOWS_UPDATE_TESTS=ON
cmake --build --preset windows-release
ctest --test-dir build/windows-msvc -C Release -R snow_windows_update_tests --output-on-failure
```

Тест создаёт собственную временную папку с пробелами и кириллицей и запускает только тестовые EXE: успешная установка, отказ нового процесса подтвердить старт и откат, блокировка целевого файла, отмена до commit, неправильный хеш, изменение payload после рукопожатия. Он проверяет сохранение старого EXE до завершения родителя и после ошибок. Тестовые EXE не входят в релиз.

Перед публикацией проверь также вручную на Windows: отключённый интернет, GitHub rate limit, каталог без прав записи, выход во время загрузки, повторные команды меню, сохранение настроек и автозапуска, непрерывность анимации во время проверки/загрузки. В среде подготовки выполнена кросс-сборка; выполнение Windows-сценариев требует Windows.
